## 2. `identity/facts.yaml` — схема

Това е **източникът на истина за Критика**. Структурирани данни, не проза — за да може всяко твърдение да се сверява машинно.

```yaml
organization:
  name_bg: "Сдружение „ИКТ-Клъстер-Варна""
  name_en: "ICT Cluster - Varna"
  eik: "175578357"
  founded: 2008
  legal_form: "сдружение с нестопанска цел, обществена полза"
  address: "бул. Сливница 189, ет. 3, офис 32, Варна"
  website: "ictclustervarna.com"

members:
  total: null              # TODO: потвърди
  full: null
  associate: null
  breakdown:
    companies: null
    universities: null
    ngos: null
    schools: null

channels:
  linkedin_followers: null # TODO: актуализира се периодично
  linkedin_url: "https://bg.linkedin.com/company/ict-cluster-varna"

programs:
  - name: "Фонд „Мост към бъдещето""
    description: ""
    sessions_held: null
  - name: "Сверяване на часовника"
    description: "годишно събитие"
    editions: null

# Всяко поле със стойност null се третира като НЕПОТВЪРДЕНО.
# Критикът маркира като недоказано всяко твърдение, което разчита на null поле.
```

Реализирай зареждането така, че `null` стойност да е **семантично различна** от липсващ ключ: `null` значи „знаем, че съществува, но не е потвърдено" — и Критикът трябва изрично да флагва твърдение, което го ползва.

## 3. `members/members.yaml` — схема

```yaml
members:
  - name: ""
    type: ""              # фирма | университет | НПО | гимназия
    linkedin_url: ""
    mention_allowed: null # TODO: изрично съгласие — null значи НЕ споменавай
    notes: ""
```

**Важно правило:** `mention_allowed: null` или `false` означава, че организацията **не се споменава по име** в автоматично генериран пост. Само `true` разрешава. По подразбиране забранено, не разрешено.

## 4. Критик — какво точно проверява

Разшири `pipeline/critic.py`. Критикът има **три отделни проверки**, всяка срещу конкретен източник:

| Проверка | Източник | Резултат при несъответствие |
|---|---|---|
| **Факти** | `facts.yaml` + `briefing.md` + `members.yaml` | Флаг за пренаписване |
| **Тон** | `voice/tone.md`, `voice/vocabulary.md` | Флаг за пренаписване |
| **Правила** | `rules/forbidden.md`, `rules/gdpr.md` | **Твърд отказ** — не се пренаписва, минава на човек |

Разграничението между последните две е съществено: нарушение на тона е повод за нов опит; нарушение на правилата спира процеса.

### Промпт на Критика — основен принцип

Вложи този принцип дословно в системния промпт:

> Провери всяко фактическо твърдение в текста. За всяко посочи източника: брифа, facts.yaml или members.yaml. Ако твърдение не може да се проследи до нито един от тези три източника — маркирай го като недоказано. Не поправяй сам и не измисляй заместващ факт. Само посочи.

Моделът **не проверява дали нещо е вярно в света** — проверява дали е **проследимо до подаден източник**. Всичко останало е халюцинация по дефиниция.

### Структуриран изход на Критика

```json
{
  "verdict": "ok | needs_revision | hard_reject",
  "facts": [
    {
      "claim": "цитат от текста",
      "source": "briefing | facts.yaml | members.yaml | UNVERIFIED",
      "note": ""
    }
  ],
  "tone_issues": [],
  "rule_violations": [
    { "rule": "gdpr | forbidden", "detail": "" }
  ],
  "summary": ""
}
```

`verdict: hard_reject` при **всяко** попадение в `rule_violations` — не подлежи на автоматично пренаписване.

## 5. Зареждане на знанието — `brand/loader.py`

Разшири така, че:

- Зарежда цялата `knowledge/` структура в един обект
- **Липсващ или празен файл не е грешка** — логва предупреждение и продължава
- Води списък кои източници са налични и кои липсват; подава го на Критика, за да знае срещу какво може и срещу какво не може да сверява
- Разделя знанието на две части в промпта: **стабилна** (identity, voice, rules — еднаква при всяко извикване) и **променлива** (брифът, снимките) — стабилната част се подава първа, за да работи кеширането на префикса

Ако `facts.yaml` липсва изцяло, Критикът **не се пропуска** — работи само с брифа като източник и отбелязва в изхода, че фактическата проверка е частична.

## 6. GDPR правило — вградено, не само в текстов файл

Независимо от съдържанието на `rules/gdpr.md`, тези три проверки се имплементират **в кода**, не се оставят на модела:

1. Пост, съдържащ име на организация с `mention_allowed != true` → `hard_reject`
2. Снимка, маркирана от vision анализа като съдържаща вероятно непълнолетни → задължителен човешки преглед, независимо от всичко останало
3. Всяко лично име в текста, което не идва от брифа → флаг

Модел, който „преценява" GDPR, не е достатъчна гаранция. Кодът е.

## 7. Какво да НЕ правиш

- Не измисляй съдържание за файловете в `knowledge/` — създай ги с TODO маркери и кратко описание какво трябва да съдържат
- Не попълвай `facts.yaml` с предположения — всичко непотвърдено остава `null`
- Не имплементирай публикуване, уеб интерфейс, база данни (както в първия промт)

## 8. Реални данни от страницата — попълни тези файлове с истинско съдържание, не TODO

Извлечени са 12 реални поста от LinkedIn страницата на клъстера. За разлика от инструкцията по-горе (празни файлове с TODO), **тези конкретни файлове се попълват сега с истинско съдържание** — анализът е направен, не се измисля.

### Наблюдавани модели (от 12 реални поста)

| Модел | Наблюдение |
|---|---|
| **Хаштагове** | **Нула поста от 12 съдържат хаштаг.** Не предполагай хаштагове никъде в кода по подразбиране. |
| **Поименна благодарност** | Във **всеки** пост — към домакини, лектори, партньори, доброволци, дори фотографа по име. Най-силният идентифициращ белег на гласа. |
| **Кука с числа/дата в началото** | „27 отбора. 76 участници. Десетки идеи." / „На 23 март проведохме..." / „Този четвъртък се събрахме..." |
| **Пълни имена и титли** | Д-р, доц., майор — винаги изписани точно, никога съкратени небрежно |
| **Emoji — тематични, не декоративни** | 🙏 благодарност · 🤝 партньорство · 📖/🔗 линк за повече · ✅ акценти (списък) · 🔹 теми на среща (списък) · 👏 поздравления. 3–6 на пост, не повече. |
| **Затваряне с линк** | „Вижте повече тук: [линк]" — почти навсякъде |
| **Дължина** | 60–150 думи, гъсто с конкретни факти и имена, не разказвателно |
| **Именувани, повтарящи се програми** | Фонд „Мост към бъдещето", ТЕХНОСТАРТ, „Сверяване на часовника" (годишно флагманско), CONNEXUS форум, Академия TechnoLab, Коледен благотворителен бал |

### `voice/tone.md` — попълни с това

```markdown
# Тон и стил

- Благодарността е структурен елемент, не украса — всеки пост благодари поименно
  на конкретни хора и организации (домакини, лектори, партньори, доброволци, фотограф).
- Отваряне с конкретен факт: число, дата или място. Не с общо въведение.
  Примери: "27 отбора. 76 участници." / "На 23 март проведохме..."
- Emoji тематични, 3–6 на пост: 🙏 благодарност, 🤝 партньорство, 📖/🔗 препратка,
  ✅ акценти, 🔹 теми, 👏 поздравления. Никога декоративни или в излишък.
- Пълни имена и официални титли винаги точни: "д-р", "доц.", "проф.", "майор".
- Затваря с покана да се види повече — линк към пълната статия/галерия.
- НЕ ползва хаштагове. Никога.
- Тон: официален, но топъл. Институционален, не корпоративен. Няма жаргон,
  няма превод-звучене от английски.
- Дължина: 60–150 думи. Гъсто с факти, не разтегнато с общи фрази.
```
