# LinkedIn Agent — ИКТ Клъстер Варна

Скелет на агент, който превръща бриф + снимки в готов LinkedIn пост на български.
**Първа стъпка** от проекта — виж [CLAUDE.md](CLAUDE.md),
[docs/prompts/agent-bootstrap-prompt.md](docs/prompts/agent-bootstrap-prompt.md),
[docs/prompts/followup-prompt-2-knowledge-critic.md](docs/prompts/followup-prompt-2-knowledge-critic.md) и
[docs/prompts/followup-prompt-3-gdpr-warnings-and-logging.md](docs/prompts/followup-prompt-3-gdpr-warnings-and-logging.md)
за пълния контекст и решенията, довели до тази структура. Публикуването в LinkedIn **не е част**
от тази фаза.

## Какво прави

Човек описва повод в `briefing.md` (или го подава директно с `--brief "текст"`, без нужда от
файл) и слага снимки в `photos/`. Агентът минава през седем стъпки и оставя **официално
предложение** в `output/post.md`, готово за ръчен преглед:

```
Планер → Писател (Post I) ‖ Media Picker → Критик → Писател (Post II)
       → Консолидатор → механични правила (код) → Критик (финална проверка)
```

**Критикът не отхвърля постове.** Каквото намери в Post I става дневен ред за Post II —
втори пълноценен пост по същия повод, който запълва тези слабости. Консолидаторът съставя
официалното предложение **от двата** поста: по-силната формулировка за всяко твърдение, без
нито една от посочените слабости, без нови факти. Накрая Критикът препрочита предложението и
само констатира какво остава открито. Конвейерът винаги стига до текст; статусът казва
единствено дали остава нещо за преглед (`ready` / `ready_with_notes`). Виж
[docs/technical/process-3.md](docs/technical/process-3.md) за пълното решение и какво
замени.

**Кое правило кой налага.** Механичните правила (кои емоджи и колко, хаштагове, дължина в
думи, маркери на списъка, непознати адреси) се **четат от `knowledge/voice/` и се налагат от
кода** — не от преценката на модел. Затова изходът е публикуем без ръчно чистене: хаштаг се
маха, неразрешено емоджи се маха, измислен домейн става `[линк]`. Всяка такава поправка се
изброява в `output/meta.json` под `applied_fixes` и в конзолата. Правило, което корпусът не
задава, не се налага. Преценката (проследимост на факти, тон, клише) остава за моделите, а
честотата, часът и реширването от лични профили — за човека. Виж
[docs/research-plans/research-plan-10-linkedin-post-craft.md](docs/research-plans/research-plan-10-linkedin-post-craft.md)
за проучването зад това и кои негови изводи са отхвърлени в полза на гласа на клъстера.

Всяка стъпка пише файл на диска. Няма база данни — състоянието е файловата система, което дава
възобновяемост: ако конвейерът спре по средата, следващото пускане продължава оттам, без да
преизчислява вече свършеното. Всяко пускане пише и хронологичен лог в `posts/<име>/run.log`.

Критикът прави три отделни проверки срещу `knowledge/` — факти (срещу брифа + `facts.yaml` +
`members.yaml`), тон (срещу `voice/`) и правила (срещу `rules/`). Всяка находка отива в дневния
ред на Post II: нарушение на `rules/forbidden.md` трябва да отпадне напълно, GDPR находка
(споменаване на организация без потвърдено съгласие, лично име извън брифа) се маха от текста,
тонови проблеми и недоказани твърдения се пренаписват. Двете GDPR проверки са вградени в кода
на Критика, не оставени на преценката на модела. Каквото оцелее до предложението, се показва
като открит въпрос в `output/meta.json`, `run.log` и в конзолата — човекът от маркетинг екипа
е крайната проверка преди публикуване.

## Инсталация

```bash
python -m venv .venv
.venv/Scripts/activate     # Windows; на Linux/Mac: source .venv/bin/activate
pip install -e ".[dev]"
cp .env.example .env       # после попълнете OPENWEBUI_API_KEY и моделите
```

## Употреба — интерактивен режим (нормалният начин)

```bash
python -m src.cli          # или: linkedin-agent
```

Отваря сесия в терминала. Пишете за какво е постът, агентът минава през конвейера
(вижда се докъде е стигнал) и отпечатва готовия текст:

```
› Клъстерът стартира стажантска програма за студенти по ИТ във Варна през септември 2026.
  posts/2026-08-11-klastarat-startira-stazhantska · без снимки
  · [1] Планер...
  · [2]/[3] Писател + Media Picker (паралелно)...
  · [4] Критик върху Post I...
  · [5] Писател → Post II (запълва 3 находки)...
  · [6] Консолидатор (Post I + Post II)...
  · [7] Критик върху предложението (информативно)...
  ─────────────────────────────────────────────
  <официалното предложение>
  ─────────────────────────────────────────────
  ✓ предложение · от post_i.md + post_ii.md · 7 извиквания · 142s

› /revise по-кратко, без клишето „вълнуващо"
```

Всеки промпт си създава своя папка `posts/<дата>-<slug>` — на диска остава същата
одитна следа, както при `generate`, но без ръчно създаване и редактиране на файлове.
`/revise` дописва инструкцията към същия `briefing.md` и пуска конвейера наново, така
че цялата история на един пост живее в една папка.

Снимки: `@C:\път\снимка.jpg` вътре в брифа, или `/attach <папка|маска>` преди него.
`/help` показва всички команди (`/again`, `/last`, `/log`, `/open`, `/check`,
`/knowledge`, `/reload`, `/exit`).

## Употреба — единични команди (за скриптове и проверки)

```bash
# провери връзката с Open WebUI и че всички модели отговарят
python -m src.cli check

# покажи кои knowledge/ файлове липсват/са празни и кои полета във facts.yaml са null
python -m src.cli check-knowledge

# създай нова папка за пост от шаблона
python -m src.cli new 2026-07-praktiki
# → редактирайте posts/2026-07-praktiki/briefing.md, сложете снимки в photos/

# генерирай поста
python -m src.cli generate posts/2026-07-praktiki

# преизчисли всички стъпки наново, независимо кои файлове вече съществуват
python -m src.cli generate posts/2026-07-praktiki --force
```

## Структура

```
knowledge/
  identity/      # about.md, history.md (проза) + facts.yaml (машинно проверими факти)
  voice/         # tone.md, formats.md, vocabulary.md
  rules/         # forbidden.md, gdpr.md — находките влизат в дневния ред на Post II; legal.md
  strategy/      # goals.md, audiences.md, pillars.md
  members/       # members.yaml — mention_allowed: true е единственото разрешение за споменаване
  examples/      # good/ (еталонни постове) и bad/ (отхвърлени + причина)
posts/<име>/     # един пост = една папка; briefing.md + photos/ на вход,
                 # plan.json / post_i.md / media.json / critique.md / post_ii.md
                 # / critique_final.md
                 # / output/ на изход
src/
  config.py      # чете .env
  errors.py      # всички грешки — всяка носи ясно съобщение какво да направи човек
  cli.py         # chat (по подразбиране) / generate / new / check / check-knowledge
  repl.py        # интерактивната сесия
  terminal.py    # UTF-8 вход/изход на Windows
  logging_utils.py  # setup_run_logger() — пише posts/<име>/run.log
  llm/           # HTTP клиент към Open WebUI, роля→модел, валидиране на JSON изход
  brand/         # зарежда knowledge/ (loader.py) + чете механичните правила (format_rules.py)
  pipeline/      # седемте стъпки + formatting.py (механичните правила) + runner.py
tests/
```

## Модели

Мапингът роля → модел е изцяло в `.env` (виж `.env.example`), не е хардкоднат в кода.
Виж таблицата в [docs/prompts/agent-bootstrap-prompt.md](docs/prompts/agent-bootstrap-prompt.md) за
кой модел за коя роля и защо. Точните идентификатори на моделите се потвърждават в Open WebUI
преди първо реално пускане — стойностите в `.env.example` са ориентировъчни.

## Обработка на грешки

Всяка грешка в `src/errors.py` носи `human_message` — изречение, което казва какво точно да
провери или направи човекът, не суров HTTP код или traceback. Частичен резултат никога не се
трие — ако конвейерът спре на стъпка 4, файловете от стъпки 1–3 остават на диска.

## Тестове

```bash
pytest
```

Фокусът на тестовете е върху обработката на грешки: retry/fallback логиката на LLM клиента,
поправящия retry при невалиден JSON, автоматичното свиване на снимки, skip-логиката за
възобновяемост, зареждането на knowledge/ (включително null-семантиката на facts.yaml), и
това, че конвейерът винаги стига до предложение: нито една присъда на Критика не хвърля
изключение, находките пътуват до Post II и до Консолидатора, а счупена стъпка 5/6/7 оставя
текст плюс обяснение в `open_notes` вместо нищо. Тества се и че код-нивото GDPR enforcement
коригира verdict в двете посоки (не само ескалира, но и понижава, ако моделът самò е сгрешил
присъдата). Няма реални мрежови извиквания в тестовете.

## Състояние на knowledge/

`voice/tone.md`, `voice/formats.md`, `identity/facts.yaml` (секция `programs`), `members/members.yaml`
и `examples/good/` вече са попълнени с реални данни, изведени от 12 действителни поста и
публичния списък членове на клъстера — виж
[docs/prompts/followup-prompt-2-knowledge-critic.md](docs/prompts/followup-prompt-2-knowledge-critic.md),
раздел 8. Всичко останало (`identity/about.md`, `identity/history.md`, `voice/vocabulary.md`,
`rules/*`, `strategy/*`, `examples/bad/`, повечето полета в `facts.yaml`) е още с `TODO` маркер —
`python -m src.cli check-knowledge` показва точно какво липсва.
